# MongoDB: de datos en memoria a una base de datos real

## El problema de los datos en memoria

Hasta ahora, `BookRepository` guardaba todo en `BOOKS_MOCK`, un array en memoria:

```typescript
export class BookRepository implements Repository<Book> {
    public findAll(): Book[] | undefined {
        return BOOKS_MOCK;
    }
    // ...
}
```

Esto nos sirvió para enfocarnos en la arquitectura (MVC, Repository Pattern), pero tiene limitaciones serias:

- **No persiste**: si reiniciamos el servidor, perdemos todos los datos.
- **No escala**: un array en memoria vive en el proceso de Node. Si levantamos dos instancias del servidor, cada una tiene su propia copia de los datos.
- **No es realista**: ninguna aplicación productiva guarda sus datos en un array de JavaScript.

Gracias al **Repository Pattern** que ya implementamos en el apunte anterior, resolver esto es simple: solo tenemos que reescribir `book.repository.ts` para que hable con una base de datos real en lugar de un array. Ni el `service` ni el `controller` se enteran del cambio — esa es la ventaja de haber invertido la dependencia en el apunte de MVC.

En este documento vamos a usar **MongoDB**, una base de datos NoSQL orientada a documentos, y vamos a comparar cada pieza de código "antes" (en memoria) y "después" (MongoDB).

## 1. Setup de MongoDB

### 1.1 Instalación local

MongoDB se puede instalar directamente en el sistema operativo como un servicio:

1. Descargar **MongoDB Community Server** desde [mongodb.com/try/download/community](https://www.mongodb.com/try/download/community).
2. Instalarlo siguiendo el instalador (en Windows queda registrado como servicio de Windows, en Mac/Linux como daemon `mongod`).
3. Opcionalmente instalar **MongoDB Compass**, un cliente gráfico para explorar bases de datos, colecciones y documentos sin usar la terminal.
4. Verificar que el servicio esté corriendo — por defecto MongoDB escucha en el puerto `27017`.

La ventaja de esta instalación es que no depende de tener Docker corriendo. La desventaja es que "ensucia" el sistema operativo con un servicio corriendo permanentemente, y que reproducir el mismo entorno en otra máquina (o en el equipo de un compañero) implica repetir toda la instalación a mano.

### 1.2 Instalación con Docker

La alternativa moderna es levantar MongoDB dentro de un **contenedor** usando Docker. Antes de ver el archivo, repasemos los conceptos:

| Concepto | Qué es | Analogía |
|---|---|---|
| **Imagen** (*image*) | Una plantilla inmutable que contiene todo lo necesario para correr un programa (sistema de archivos, binarios, configuración por defecto) | La "receta" o el molde |
| **Contenedor** (*container*) | Una instancia en ejecución de una imagen, aislada del resto del sistema operativo | Un proceso corriendo a partir del molde |
| **Volumen** (*volume*) | Un espacio de almacenamiento gestionado por Docker que vive fuera del contenedor, para persistir datos aunque el contenedor se elimine | El "disco externo" que sobrevive aunque tires el contenedor a la basura |
| **Stack / Compose** | Un conjunto de servicios (contenedores) definidos en un mismo archivo, que se levantan y comunican entre sí | El plano de una instalación completa (todas las piezas que la app necesita) |

¿Por qué importa el volumen? Un contenedor es, por diseño, **descartable**: si lo eliminamos (`docker rm`), todo lo que haya en su sistema de archivos interno desaparece con él. Si MongoDB guardara sus datos *dentro* del contenedor, perderíamos la base de datos cada vez que lo recreamos (por ejemplo, al actualizar la imagen). El volumen resuelve esto: es una carpeta gestionada por Docker en la máquina host, que se "monta" dentro del contenedor. El contenedor escribe ahí, pero esa carpeta no se borra cuando el contenedor se destruye.

Este es el `docker-compose.yml` que agregamos en la raíz del proyecto:

```yaml
services:
  mongo:
    image: mongo:latest
    container_name: DSW-UTN-Mongo
    restart: unless-stopped
    ports:
      - "27017:27017"
    volumes:
      - dsw-utn-mongo-data:/data/db
    networks:
      - dsw-utn-net

  postgres:
    image: postgres:latest
    container_name: DSW-UTN-Postgres
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD: dsw_123!
    ports:
      - "5432:5432"
    volumes:
      - dsw-utn-postgres-data:/var/lib/postgresql/data
    networks:
      - dsw-utn-net

networks:
  dsw-utn-net:
    name: dsw-utn-net

volumes:
  dsw-utn-mongo-data:
  dsw-utn-postgres-data:
```

Desglosemos cada clave:

- **`services`**: cada entrada bajo `services` (`mongo`, `postgres`) es un contenedor que Compose va a gestionar. En este archivo definimos un *stack* con dos servicios: MongoDB (que vamos a usar ahora) y PostgreSQL (que se agrega ya para una clase futura, pero no lo vamos a usar todavía).
- **`image: mongo:latest`**: la imagen que se descarga de Docker Hub. `mongo` es el nombre oficial de la imagen de MongoDB; `latest` es el tag de versión (podríamos fijar una versión concreta, como `mongo:7`, para reproducibilidad).
- **`container_name`**: nombre fijo para identificar el contenedor con `docker ps` en lugar de un nombre aleatorio generado por Docker.
- **`restart: unless-stopped`**: si el contenedor se cae o si reiniciamos la máquina, Docker lo vuelve a levantar automáticamente, salvo que lo hayamos parado nosotros manualmente.
- **`ports: "27017:27017"`**: mapea el puerto 27017 del contenedor al puerto 27017 de nuestra máquina (`host:container`). Sin este mapeo, MongoDB estaría aislado dentro del contenedor y nuestra API (que corre en el host) no podría conectarse.
- **`volumes: dsw-utn-mongo-data:/data/db`**: monta el volumen nombrado `dsw-utn-mongo-data` en `/data/db`, que es la carpeta donde MongoDB escribe sus archivos de datos dentro del contenedor. Docker crea y gestiona ese volumen — no necesitamos saber en qué carpeta física del sistema operativo vive.
- **`networks`**: ambos servicios comparten la red `dsw-utn-net`. Esto les permite comunicarse entre sí por nombre de servicio (por ejemplo, desde otro contenedor podríamos conectarnos a `mongo:27017` en lugar de `localhost:27017`). Para nuestra API, que corre fuera de Docker (en el host), esto no es estrictamente necesario todavía, pero es la base para el día que "dockericemos" también la API.
- **`volumes:` (nivel raíz)**: acá se *declaran* los volúmenes nombrados que los servicios referencian. Es necesario declararlos para que Docker los cree la primera vez.

Para levantar el stack:

```bash
docker compose up -d
```

`-d` (*detached*) corre los contenedores en segundo plano. Para verificar que MongoDB está corriendo:

```bash
docker ps
```

Para bajar el stack (los contenedores se eliminan, pero el volumen persiste):

```bash
docker compose down
```

> La ventaja frente a la instalación local es la **reproducibilidad**: cualquier persona del equipo con Docker instalado ejecuta un solo comando y tiene exactamente el mismo entorno, con la misma versión de Mongo, sin "ensuciar" su sistema operativo.

## 2. MongoDB Shell: operaciones básicas

Con el contenedor corriendo, podemos conectarnos a la base de datos usando `mongosh` (el shell de MongoDB) para ejecutar comandos directamente. Podemos abrirlo desde la terminal o desde MongoDB Compass.

Usamos como referencia el archivo de seed del proyecto: `api/db/mongo/seed/seed_mongo.js`.

### Seleccionar (o crear) una base de datos

```javascript
use book_champions
```

MongoDB no tiene un paso explícito de "crear base de datos": simplemente empieza a existir la primera vez que insertamos un documento en ella. Lo mismo pasa con las **colecciones** (el equivalente a una tabla en SQL): `db.books` se crea automáticamente al insertar el primer documento.

### Insertar documentos

```javascript
db.books.insertOne({
  title: 'The Fellowship of the Ring',
  authors: ['J.R.R. Tolkien'],
  publisher: 'Allen & Unwin',
  pageCount: 423,
  rating: 4.8,
  cover: 'fellowship-of-the-ring.jpg',
  isAvailable: true,
})

db.books.insertOne({
  title: "Harry Potter and the Philosopher's Stone",
  authors: ['J.K. Rowling'],
  publisher: 'Bloomsbury',
  pageCount: 223,
  rating: 4.7,
  cover: 'philosophers-stone.jpg',
  isAvailable: true,
})
```

- `db` hace referencia a la base de datos actualmente seleccionada (`book_champions`).
- `db.books` hace referencia a la colección `books` dentro de esa base de datos.
- `insertOne(...)` recibe un objeto JavaScript plano — no hay un esquema fijo que validar como en SQL. Cada documento puede, en principio, tener campos distintos (aunque en la práctica mantenemos una forma consistente).
- MongoDB agrega automáticamente un campo `_id` de tipo `ObjectId` a cada documento insertado, que funciona como clave primaria única.

### Consultar documentos (`find`)

```javascript
// Todos los documentos de la colección
db.books.find()

// Filtrar por igualdad
db.books.find({ publisher: 'Bloomsbury' })

// Filtrar con operadores: rating mayor a 4.7
db.books.find({ rating: { $gt: 4.7 } })

// Proyección: solo devolver title y publisher (además de _id, que viene por defecto)
db.books.find({ rating: { $gt: 4.7 } }, { title: 1, publisher: 1 })

// Excluir _id explícitamente de la proyección
db.books.find({ rating: { $gt: 4.7 } }, { title: 1, publisher: 1, _id: 0 })

// Buscar por _id puntual (el valor cambia según lo que haya generado Mongo)
db.books.find({ _id: ObjectId('65155fb42f53abe42bd53cee') })
```

Puntos clave:
- El primer argumento de `find` es el **filtro** (equivalente al `WHERE` de SQL).
- El segundo argumento es la **proyección**: qué campos incluir (`1`) o excluir (`0`) del resultado.
- `$gt` es un **operador de query** (*greater than*). MongoDB tiene una familia entera: `$gte`, `$lt`, `$lte`, `$ne`, `$in`, etc.
- `ObjectId(...)` reconstruye el identificador binario de 12 bytes a partir de su representación en string hexadecimal.

### Actualizar documentos (`updateOne`)

```javascript
db.books.updateOne(
  { title: 'The Fellowship of the Ring' },
  { $set: { title: 'The Lord of the Rings: The Fellowship of the Ring', isAvailable: false } }
)
```

- El primer argumento es el filtro que identifica **qué** documento actualizar (si hay varios que matchean, `updateOne` solo modifica el primero que encuentra).
- El segundo argumento describe **qué cambiar**. `$set` reemplaza únicamente los campos indicados, dejando el resto del documento intacto — es el equivalente a un `UPDATE ... SET columna = valor` en SQL, pero sin tocar las demás columnas.

### Eliminar documentos (`deleteOne`)

```javascript
db.books.deleteOne({ isAvailable: false })
```

Elimina el primer documento que matchea el filtro. Existe también `deleteMany` para borrar todos los que coincidan.

> Para ejecutar todo el seed de una vez: `mongosh book_champions api/db/mongo/seed/seed_mongo.js`, o pegar el contenido del archivo directamente en `mongosh`.

## 3. Conexión desde la API: `conn.ts`

Para que nuestra API en TypeScript hable con MongoDB, instalamos el paquete oficial:

```json
"dependencies": {
    "express": "^5.2.1",
    "mongodb": "^7.5.0"
}
```

Y creamos un archivo dedicado a la conexión, `src/shared/db/conn.ts`:

```typescript
import { Db, MongoClient } from "mongodb";

const connectionString = process.env.MONGODB_URI || 'mongodb://localhost:27017/';

const client = new MongoClient(connectionString);
await client.connect();

export let db: Db = client.db('book_champions');
```

- **`MongoClient`**: la clase del paquete que administra la conexión (y el *pool* de conexiones) contra el servidor de MongoDB.
- **`connectionString`**: la URI de conexión. Se lee de la variable de entorno `MONGODB_URI` si existe (útil para producción o para apuntar a un contenedor con otro host/puerto), y si no, cae al valor por defecto `mongodb://localhost:27017/`, que apunta al contenedor de Docker que expusimos en el puerto 27017 del host.
- **`await client.connect()`**: es un **top-level await** — código `await` fuera de una función `async`. Esto es válido gracias a `"module": "NodeNext"` en `tsconfig.json`, que habilita ES Modules nativos en Node. El archivo se ejecuta una sola vez (la primera vez que algo lo importa) y bloquea hasta que la conexión esté establecida antes de que el resto de la app siga cargando.
- **`export let db: Db`**: exportamos la instancia de la base de datos ya conectada. Cualquier repositorio que necesite acceso a Mongo importa este `db` en lugar de crear su propia conexión — así garantizamos una única conexión compartida en toda la aplicación.

Este archivo vive en `shared/db/` porque, igual que `base.repository.ts`, es una pieza de infraestructura genérica: no sabe nada de libros ni de ningún dominio en particular, solo sabe cómo conectarse a la base.

En términos de Clean Architecture (ver `[[1.1 - MVC]]`), `conn.ts` pertenece al anillo más externo (**Frameworks & Drivers**): es el detalle técnico de *cómo* nos conectamos a una base de datos concreta.

## 4. Operaciones básicas del repositorio: antes vs. después

Con la conexión lista, reescribimos `book.repository.ts` para que use la colección `books` de Mongo en lugar del array `BOOKS_MOCK`. Antes de entrar en cada método, dos cambios transversales:

**Todo pasa a ser asíncrono.** Consultar una base de datos implica una operación de red, que en Node.js es inherentemente asincrónica. Esto obliga a propagar `async`/`await` (y `Promise`) por las tres capas:

```typescript
// shared/base.repository.ts — ANTES
export interface Repository<T> {
    findAll(): T[] | undefined,
    findOne(item: { id: string }): T | undefined,
    add(item: T): T | undefined,
    update(item: T): T | undefined,
    delete(item: { id: string }): { id: string } | undefined
}

// shared/base.repository.ts — DESPUÉS
export interface Repository<T> {
    findAll(): Promise<T[] | undefined>,
    findOne(item: { id: string }): Promise<T | undefined>,
    add(item: T): Promise<T | undefined>,
    update(item: T): Promise<T | undefined>,
    delete(item: { id: string }): Promise<{ id: string } | undefined>
}
```

Como el `service` depende de esta interfaz (Dependency Inversion — ver `[[1.1 - MVC]]`), el cambio se propaga automáticamente a `book.service.ts`:

```typescript
// book.service.ts — ANTES
findAll(): Book[] | undefined {
    return this.repo.findAll();
}

// book.service.ts — DESPUÉS
findAll(): Promise<Book[] | undefined> {
    return this.repo.findAll();
}
```

Y a su vez a `book.controller.ts`, que ahora debe `await` cada llamada al service:

```typescript
// book.controller.ts — ANTES
export const findAll = (req: Request, res: Response) => {
    res.json(service.findAll());
}

// book.controller.ts — DESPUÉS
export const findAll = async (req: Request, res: Response) => {
    const books = await service.findAll();
    res.json(books);
}
```

Este es exactamente el punto que resalta el Repository Pattern: cambiamos **cómo** se guardan los datos (de sincrónico en memoria a asincrónico contra una base real), y ese cambio se filtra hacia arriba únicamente como una firma de tipos (`Promise<...>`) — la *lógica* del controller y del service no cambió en absoluto.

**El identificador cambia de forma.** En la versión en memoria, `Book` generaba su propio `id` con `crypto.randomUUID()`. MongoDB, en cambio, genera su propio identificador (`_id`, de tipo `ObjectId`) al insertar un documento. Por eso la entidad ahora tiene ambos campos:

```typescript
// book.entity.ts — DESPUÉS
import { ObjectId } from "mongodb";
import crypto from "node:crypto"

export class Book {
    constructor(
        public title: string,
        public authors: string[],
        public publisher: string,
        public pageCount: number,
        public rating: number,
        public cover: string,
        public isAvailable: boolean,
        public id = crypto.randomUUID(),
        public _id?: ObjectId
    ) { }
}
```

`_id` queda opcional (`?`) porque no existe hasta que Mongo lo asigna en el momento del `insertOne`.

Con esto en mente, veamos cada operación del repositorio.

### 4.1 `findAll`

```typescript
// ANTES
public findAll(): Book[] | undefined {
    return BOOKS_MOCK;
}

// DESPUÉS
public async findAll(): Promise<Book[] | undefined> {
    return await books.find().toArray();
}
```

- Antes: devolvíamos directamente la referencia al array en memoria.
- Después: `books.find()` (sin filtro) devuelve un **cursor** — un objeto que permite iterar los resultados sin traerlos todos a memoria de una sola vez. `.toArray()` consume ese cursor y materializa todos los documentos en un array, que es lo que esperan el `service` y el `controller`.

### 4.2 `findOne`

```typescript
// ANTES
public findOne(item: { id: string; }): Book | undefined {
    return BOOKS_MOCK.find((book) => book.id === item.id);
}

// DESPUÉS
public async findOne(item: { id: string; }): Promise<Book | undefined> {
    const _id = new ObjectId(item.id);
    return await books.findOne({ _id }) || undefined;
}
```

- Antes: recorríamos el array a mano con `Array.prototype.find`, comparando el `id` (uuid) de cada libro.
- Después: delegamos la búsqueda a Mongo. `new ObjectId(item.id)` reconstruye el identificador binario a partir del string recibido por parámetro (por ejemplo, desde `req.params.id`), y `books.findOne({ _id })` filtra directamente en la base de datos por ese identificador.
- **`|| undefined`**: `findOne` de Mongo devuelve `null` cuando no encuentra nada, pero nuestra interfaz `Repository<T>` promete `T | undefined`. El `|| undefined` normaliza ese `null` a `undefined` para respetar el contrato.

> Nota importante: al migrar a Mongo, el identificador que realmente usamos para buscar, actualizar y borrar pasa a ser el `_id` autogenerado por la base de datos, no el `id` (uuid) que la entidad seguía generando en el constructor. Es una inconsistencia a tener en cuenta en esta etapa de la migración: el objeto `Book` todavía carga un `id` que ya no es la clave real utilizada contra la base.

### 4.3 `add`

```typescript
// ANTES
public add(item: Book): Book | undefined {
    BOOKS_MOCK.push(item);
    return item;
}

// DESPUÉS
public async add(item: Book): Promise<Book | undefined> {
    item._id = (await books.insertOne(item)).insertedId
    return item;
}
```

- Antes: agregábamos el objeto al final del array.
- Después: `books.insertOne(item)` persiste el documento en la colección y devuelve un objeto con metadata de la operación, entre ella `insertedId` — el `ObjectId` que Mongo generó (o usó, si se lo hubiéramos pasado). Se lo asignamos de vuelta a `item._id` antes de devolverlo, para que quien reciba el `Book` tenga también su identificador real de Mongo.

### 4.4 `update`

```typescript
// ANTES
public update(item: Book): Book | undefined {
    const bookIndex = BOOKS_MOCK.findIndex(book => book.id === item.id);

    if (bookIndex >= 0) {
        BOOKS_MOCK[bookIndex] = { ...BOOKS_MOCK[bookIndex], ...item }
    }

    return BOOKS_MOCK[bookIndex];
}

// DESPUÉS
public async update(item: Book): Promise<Book | undefined> {
    const { id, ...bookInput } = item;
    const _id = new ObjectId(id)
    return await books.findOneAndUpdate({ _id }, { $set: bookInput }, { returnDocument: 'after' }) || undefined;
}
```

- Antes: buscábamos el índice del libro en el array y hacíamos un *merge* manual con spread (`{ ...viejo, ...nuevo }`), quedándonos con el índice actualizado.
- Después: usamos `findOneAndUpdate`, el equivalente atómico de "buscar y actualizar en una sola operación":
  - `{ id, ...bookInput }` desestructura el objeto para separar el `id` (que no queremos escribir como campo dentro del documento) del resto de los campos a actualizar.
  - `{ $set: bookInput }` le indica a Mongo que solo modifique los campos presentes en `bookInput`, dejando el resto del documento (incluido `_id`) intacto — el mismo operador `$set` que vimos en el shell.
  - `{ returnDocument: 'after' }` le pide a Mongo que devuelva el documento **después** de aplicar la actualización (por defecto, sin esta opción, devolvería el documento *antes* del cambio).

### 4.5 `delete`

```typescript
// ANTES
public delete(item: { id: string; }): { id: string } | undefined {
    const bookIndex = BOOKS_MOCK.findIndex((book) => book.id === item.id);

    if (bookIndex >= 0) {
        BOOKS_MOCK.splice(bookIndex, 1);
    }

    return { id: item.id }
}

// DESPUÉS
public async delete(item: { id: string; }): Promise<{ id: string } | undefined> {
    const _id = new ObjectId(item.id);
    return await books.findOneAndDelete({ _id }) || undefined;
}
```

- Antes: buscábamos el índice y usábamos `splice` para remover el elemento del array in-place.
- Después: `findOneAndDelete` busca y elimina el documento en una sola operación atómica contra la base, devolviendo el documento eliminado (o `null`, normalizado a `undefined`).

## Resumen: qué cambió y qué no

| Capa | ¿Cambió? | Detalle |
|---|---|---|
| `book.entity.ts` | Sí (mínimo) | Se agrega `_id?: ObjectId` opcional junto al `id` (uuid) existente |
| `base.repository.ts` | Sí | Todos los métodos ahora retornan `Promise<...>` |
| `book.service.ts` | Sí (solo tipos) | Se propagan los `Promise<...>` de la interfaz; la lógica interna no cambia |
| `book.controller.ts` | Sí (solo async/await) | Cada handler se vuelve `async` y agrega `await` antes de llamar al service |
| `book.repository.ts` | **Totalmente reescrito** | Es la única capa que sabe que ahora hablamos con MongoDB en lugar de un array |
| `book.routes.ts` | No | Las rutas HTTP no cambian |
| `app.ts` | No | El punto de entrada no cambia |

Esta es la prueba de que la arquitectura en capas cumplió su promesa: migrar de datos en memoria a una base de datos real implicó reescribir **un solo archivo** de lógica de negocio real (`book.repository.ts`), y propagar cambios puramente mecánicos de tipos (`Promise`, `async/await`) por el resto de las capas que dependen de la interfaz `Repository<T>`.
